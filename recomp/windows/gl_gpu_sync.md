# Native GPU fence lifecycle

The selected original Unity path uses core `glFenceSync`, `glClientWaitSync`, and `glDeleteSync`. `GlHost` appends those three exports after the existing 150 marker identities. Query, server-wait, and extension aliases are not added.

Fence handles are the native ANGLE `GLsync` bit patterns passed through the full 64-bit guest ABI. They are opaque handles, not guest-addressable memory or replacement adapter tokens. Native ANGLE owns creation, validation, share-group ownership, completion, error flags, deletion, and cleanup when the native share group is destroyed. Client waits pass flags and the full unsigned 64-bit nanosecond timeout unchanged; results are the actual native wait result, without forced completion or timing substitution.

Context selection and diagnostic accounting happen under the existing provider mutex. Only the immutable `glClientWaitSync` callback is copied while locked and invoked after releasing that mutex; the path returns immediately without reading provider context fields or updating counters afterward. Other APIs retain their locking behavior. This permits independent contexts to make progress while a client wait is active. ANGLE retains its own share-group synchronization; concurrent operations within one share group have the native driver's guarantees. All provider calls must finish before provider destruction.

The observed original failure establishes a fence creation request (`GL_SYNC_GPU_COMMANDS_COMPLETE`, flags zero). The same original function contains zero-timeout client polling and deletion, and stores its fence handle as 64 bits. An actual successful original swap, render return, or first-frame capture is not claimed by this port.
